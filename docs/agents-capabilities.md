# Capability agents vs. permanent personas (STORY-017)

AgentForge v2 does not generate a mandatory persona roster. `/agentforge:setup`
writes only `.agentforge/config.json` and a small constitution pointer block
(STORY-005) — it never generates an `interviewer`, `planner`, `scaffolder`,
`dev`, `tester`, or `final-judge` agent file into a project, and it never
enables a bundled capability agent on a project's behalf. This document
explains why, and when reaching for one of the two bundled agents is worth
it.

## Two different tools solving two different problems

**A permanent persona** (v1's project-bootstrap roster, still generated by
the legacy `bootstrap`/`add-agent` flow into `.claude/agents/*.md` or
`.codex/agents/*.toml` until STORY-019 retires it) is a project-specific
file, committed to the repo, always present, with a fixed model assignment
and a role name the team is expected to remember and route work through
("assign this to `dev`", "have `tester` verify it"). It is ceremony that
pays for itself only when a project's workflow genuinely benefits from a
stable division of labor across an entire multi-phase roadmap.

**A capability agent** (`independent-reviewer`, `verifier`) is a bundled,
optional subagent with no project file at all — it ships inside the
AgentForge plugin itself, the same way Claude Code's built-in `Explore` and
`Plan` agents are always available without any project configuration. It
exists to grant a *distinct runtime capability* — an isolated context
window, a restricted tool set — for one invocation, not to occupy a
permanent role in a roadmap.

## When a subagent is preferable to a permanent persona

Reach for a capability agent (a subagent), not a persona, when:

- **You need tool-grant isolation, not role-play.** The value is that the
  agent *cannot* do something (edit source, run an undeclared command), not
  that it "acts like" a reviewer or tester. A frontmatter `tools:` list
  enforces this structurally; a persona's system prompt asking an
  unrestricted agent to "please don't edit files" does not.
- **You need context isolation for one decision, not a standing role.** An
  independent review is more valuable when it comes from a context window
  that never saw the implementation discussion — that property only holds
  for an on-demand subagent invocation, not a persona that has been part of
  the same long-running conversation.
- **The task is occasional, not load-bearing for the whole project.** A
  second look before a risky merge, or a tamper-proof verification pass
  before declaring a story done, does not justify a permanent, always-on
  agent file that every contributor has to know exists and keep in sync
  with the roadmap.

A permanent persona can still make sense for a project's ordinary
implementation loop — that is what v1's project-bootstrap flow (unchanged
by this story) continues to provide until STORY-019. The point of this
story is narrower: AgentForge itself does not force that roster on every
project by default, and its own two bundled agents are capability grants,
not roles.

## The two bundled capability agents

Both are defined in `agents/` at the root of the AgentForge plugin
(`agents/independent-reviewer.md`, `agents/verifier.md`), available the
moment the plugin is installed, and invoked explicitly — never
automatically — via the `Agent` tool, e.g.
`Agent(subagent_type="agentforge:independent-reviewer", ...)`.

### `independent-reviewer`

- **Concrete benefit:** a second, unbiased look at a diff or a
  spec-compliance question from a context window with no memory of why the
  code was written that way, with tool grants that make it *impossible* for
  it to "fix while reviewing."
- **Tools:** `Read`, `Grep`, `Glob`, and a short read-only `Bash` allow-list
  (`git log`, `git diff`, `git show`, `git blame`, `git status`, `rg`,
  `grep`, `find`, `ls`, `cat`, `wc`). No `Write`, `Edit`, `MultiEdit`,
  `NotebookEdit`, or unrestricted `Bash`.
- **Model:** `inherit` — no dated model id is pinned; a project may pin an
  explicit model in its own copy of the definition if it wants
  reproducibility, per the execution plan's model-routing guidance.
- **When to use it instead of Matt's `code-review` skill:** for a
  higher-stakes review where isolation from the implementing conversation's
  framing matters more than speed. Routine review should keep using
  `code-review`.

### `verifier`

- **Concrete benefit:** tamper-proof confirmation that "done" is actually
  true. It runs only the verification commands the active work contract
  declares (`.agentforge/active-work.json`, STORY-008) or commands named
  explicitly by the caller, and reports exact exit status and output. It
  cannot edit anything, so a PASS verdict cannot be the result of a patch
  applied after the check ran.
- **Tools:** `Read`, `Bash`. No `Write`, `Edit`, `MultiEdit`, or
  `NotebookEdit` — the agent is structurally unable to modify source, only
  to run commands and read files.
- **Model:** `inherit` — no dated model id is pinned.
- **When to use it:** before declaring a story or ticket complete, as an
  independent check that does not share the implementing conversation's
  incentive to see green.

## Both are off by default

- `templates/agentforge-config.json` ships with `scope.agents: {}` and
  `scope.mode: "off"` — no agent is enabled by the shipped config.
- `/agentforge:setup`'s `plan`/`apply` transaction (`scripts/setup.py`)
  never proposes or writes a file under `agents/`, `.claude/agents/`, or
  `.codex/agents/`; it only ever touches the constitution pointer block and
  `.agentforge/config.json`. Enabling a capability agent is never part of
  that transaction.
- Using either bundled agent requires an explicit `Agent(...)` invocation
  naming it. Optionally registering its identity under `scope.agents.<name>`
  in `.agentforge/config.json` (for a future graded scope-policy engine,
  STORY-013/014) is a separate, explicit, hand-made edit to an
  already-committed file — never something setup writes automatically.

## Identity used by scope hooks (STORY-014)

Each bundled agent's frontmatter `name:` field (`independent-reviewer`,
`verifier`) is its `agent_type` identity — the same string a future graded
scope hook matches against `scope.agents.<name>` in `.agentforge/config.json`
(see `docs/agentforge-config.md`). `tests/test_agents.py` asserts this
identity matches the filename and validates end-to-end through
`scripts/config.py`.
